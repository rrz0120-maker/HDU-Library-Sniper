基于 `feat/android-p51-userscript` 的 `5cbb65a`。本次只修复日期解析、日期选项及只读诊断，更新版本为 **5.2.0**；登录、座位解析、签名、单次提交函数和 IndexedDB 防重复保护不变，没有改动 V3.0 的预约调度规则。

## 已确认的日期契约

用户的一加 Firefox + Tampermonkey 已成功运行，日志有 `LOGIN_OK`，登录检查约41–113ms；以下数字来自用户提供的真实只读日志，不是模拟猜测：

| 字段 | 原值（number，Unix秒） | UTC | Asia/Shanghai |
|---|---:|---|---|
| advance_date | 1794758400 | 2026-11-15 16:00 | **2026-11-16 00:00** |
| max_date | 1795017600 | 2026-11-18 16:00 | **2026-11-19 00:00** |

保留 `YYYY-MM-DD` 字符串兼容。数字必须是安全整数、非负且小于 `10^10`（秒量级），乘1000后必须精确等于上海零点，并通过 `Intl.DateTimeFormat` 的 `Asia/Shanghai` 零时零分零秒检查。不自动除1000“修正”毫秒数据；拒绝浮点、非有限值、不安全整数、毫秒量级、数字字符串、非零点、无效日历日期、倒置范围、超过31天的跨度。相同起止边界表示空范围。

### max_date 不包含当天

只读获取了官网入口实际引用的[公开前端资源](https://hdu.huitu.zhishulib.com/rwpublic/js/app.es6.min.js)，其“使用日期”控件的两个方法为：

```javascript
// 以下为保留语义的简写，原文片段与资源SHA256见证据文件。
days = (midnight(max_date) - midnight(default.date)) / 86400;
for (n = 0; n < days; n++) dates.push(default.date + n * 86400);
```

因此控件使用**不包含上界**的日期区间。P5.1 的 `<= max_date` 多列一天，本次纠正为 `< max_date`，对时间戳和日期字符串一致处理。这组范围列出 **11月16、17、18日**，**不列出19日**；日志 `DATES_OK.maxDateExclusive` 会标注 `2026-11-19`。

证据：[原始方法片段、URL、读取时间和 SHA256](evidence/p52/date-control.json)。仅获取未登录公共入口及其一个 JS 资源，未使用校园会话，未调用预约写入端点。官网控件起点使用 `data.default.date`；当前脚本沿用接口 `advance_date` 作范围起点，用户这份日志没有 `default.date`，请继续与手机原生日期控件核对首末日期。

### 与 V3.0 “20:00开放当天+2”的关系

若这份日志采集于11月16日，排除上界后的最后日期是11月18日，日期上是“当天+2”，不能据 `max_date=11月19日` 判成开放了“当天+3”。但**没有日志采集的北京时间、20:00前后对照，以及正式写入开放状态证据**；日期控件可选也不等于预约写入已开放。

因此本次不能证明或推翻“20:00才开放当天+2”。`crates/core/src/time.rs`、`crates/server/src/strict.rs` 等正式规则保持原样，不通过真实提交来探测开放时点，不实现20:00手机模式。
