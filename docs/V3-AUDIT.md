## 不变的接口契约

来自 `crates/hdu/src/library/booking.rs`：`beginTime` 为 UTC Unix 秒，`duration=14*3600`，`seats[0]` 为目录解析出的 ID，`seatBookers[0]` 为已验证 UID，`api_time` 和 `Api-Token` 继续由原 Rust 实现生成。仅一个 seat/booker，人数为 1。没有自行猜测内部 ID 或签名。

房间通过 `roomName` 的精确别名匹配；其中无楼层后缀的“宋韵云图”依据本任务指定的区域名称。真实环境必须只读核对它确实对应四楼；若名称变更，不做模糊回退。

当前上游解析器只公开四个小时/时长边界，没有可核验的 `advance_date/max_date` 类型契约。本实现使用用户明确指定的“上海当天 +2、20:00 开放”，并检查服务端小时及14小时上限；**没有编造未知字段格式**。若馆方开放规则变化，停止部署并更新契约测试。

## 状态与请求上限

- 每次任务唯一键固定，不随着重启或跨日改变。
- WAITING → CHECKING → CHECKED → PREPARING → READY → RUNNING。
- 预约写前原子提交 SUBMITTING_162 或 SUBMITTING_157 与 attempts；只有赢得 CAS 的进程能够发出请求。
- 成功须由记录中的房间、座位、开始时间和50400秒时长核对。仅收到成功字样不足以成功。
- 只有 `ParamError` 明确座位不可用，且记录查询成功且无冲突，才可在至少10秒后尝试157。
- 404、超时、格式错误、未到开放时间、成功响应但记录无法确认：UNKNOWN，停止；不通过重新开始绕过。
- 频繁/封禁/HTTP429/403：LIMITED；认证失效：AUTH_REQUIRED；均立即停止。
- UNKNOWN、LIMITED、AUTH_REQUIRED、两座均失败会关闭每日开关，需用户重新检查后启用。
- 用户停止在一个事务中关闭每日模式并终止未完成任务；同时发生的自动建任务不能越过该事务。
- 已发出的网络请求不能撤回；停止后显示“可能已完成，请核对官方记录”，不会伪称取消成功。
- 每任务正式预约写最多2次；没有 lock、unlock、cancel、签到请求。执行前和每次提交后各至多一次预约记录核验。无高峰轮询风暴。

## 缓存与恢复

19:58 用**次日已开放时段**读取映射，忽略 POI.state，绝不以此判断后天可用。缓存带房间、楼层、编号对应 ID、验证时间和校验和，最长10分钟；校验和用于发现意外损坏，不是防恶意数据库篡改的签名。每日重新解析，不硬编码内部 ID。

WAITING/CHECKED/READY 可以恢复。执行中认领（CHECKING/PREPARING/RUNNING/SUBMITTING）不重新认领，以安全停机换取防重复；UI 超过120秒提示中断/待确认。这个保守策略可能放弃一次机会。服务器应避免19:55–20:10更新。不能删除任务行或恢复旧数据库后再次抢同一日期。

缓存有效期内馆方瞬时更改 ID 映射无法完全排除；真实只读验证是上线前提。任务只会使用唯一匹配的区域和两个编号。不能保证抢到座位。

## 时钟与部署边界

上海时区独立于宿主机 TZ；每次写前还会验证登录 UID、HTTP Date 偏差≤2秒、样本新鲜度<10分钟。开放门禁还取本地时间与服务端Date+单调时钟的较早值，防止本地稍快导致提前提交。HTTP Date 只是粗检查，网络延迟可能让它保守拒绝；宿主机仍须使用 chrony/systemd-timesyncd，并检查同步状态。只在本地开放时间后发起，不使用未来日期提前预锁。

严格模式隔离所有旧方案/预约/取消/签到写路由，后台也不启动旧调度器。旧桌面模式保留，部署不得将 HDU_STRICT_MODE 改成0来绕过严格保护。
